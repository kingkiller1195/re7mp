# RE7 multiplayer: change history

The history of every build, newest first. What the mod does *now* is in README.md.

## What changed in v9.44 (release 0.9; same protocol v6; **update `re7mp.lua` on both computers; no exe change**)

Your 2026-11-14 02:08 note: key items like the fuse and the bolt cutters are taken from both games, so a pickup that is taken and then consumed or used by one player would break the other's game. Then, at 02:12: "if it ships with only sharing consumables and guns, then leave it on". So item sync **stays on, but now shares only consumables and weapons.** **Unverified in the real game:** it is checked against a fake game; the category is read from the real record the game's own dump shows (`app.Item.get_ItemData()` / `_ItemData`, `app.ItemData.Category`, enum `app.Item.ItemCategoryType`), which is how the first real run will confirm it.

**What changed**
1. **Only these are shared:** weapon (1), ammo / shell (2), heal / drug (3), material (7, the chemicals and the like, consumed in crafting) and stack weapon (8, throwables). **Never shared:** key item (4), file (5), map (6), usable key item (9), discardable key item (10), supply box (11), other item (0), and anything whose category can't be read (nothing is shared that can't be classified).
2. **Both sides check.** The player who picks an item up sends it only if it is on the list. The player who receives the message looks at the item lying in their own world (its own record) before removing it, so an older script on the other computer that sends everything can't take a key item out of this game either.
3. **A weapon goes to whoever picks it up first, even in "both players get it" mode:** it is removed on the other screen, so one of you can have the double barrel and the other the second shotgun when they find it. Heals and ammo still stay on both screens in "both" mode.
4. **A new box, "Share only consumables and weapons"** (on; remembered as `item_safe_only`, and shipped on). Unticking it shares everything as before, with a warning line in the panel. The old sharing mechanics (the 3 m rule for gifts, the ground route) are untouched.
5. **Debug file:** `health.item_sync` gains `only_consumables_and_weapons`, `not_shared_key_items_and_the_like`, `category_unreadable`, `weapons_taken_for_the_other_player` and `categories_seen` (item id -> category name), and each pickup ring line says why an item was not sent.

**Not changed:** a settings file from an older build keeps its own choice (sync ticked stays ticked, now with the filter); the shipped `defaults.json` has `item_sync` on and `item_safe_only` on (a new shipped key: 54 settings).

**Tests:** Lua Scenario 26 (a new player: on and filtered; a heal / ammo / weapon / material sent and a key item / usable key item / file / other item / unreadable category not sent; the counts and category names in the debug file; unticking the filter shares everything with a warning and is remembered; 'take' mode removes a heal and leaves a key item and an unreadable item; 'both' mode keeps a heal, takes a weapon and keeps a key item; filter off + 'both' is as it was; an older settings file keeps sync with the filter; the panel text). The older item checks (mechanics) run with the filter off.

**Still open:** that the real game's `get_ItemData` / `Category` read works as the dump shows (the first pickup lines in the log say `category` or "can't be read"), which item ids are which category (the debug file now collects them), and everything that needs a second player.

## What changed in v9.43 (release 0.9; same protocol v6; **update `re7mp.lua` on both computers; no exe change**)

Your request: "a log that detects when Mia spawns, then check which methods the game calls to spawn her, as well as which files it loads. That way you'll know for sure if something is missing" (for the Mia hair, and for finding hair physics on characters and enemies). **Unverified in the real game:** the whole module is checked against a fake game; which classes and methods it finds, and what Mia's real objects hold, is what your first run will tell. It only reads: nothing is changed in the game.

**What it is:** a new panel node "Spawn log: Mia's spawn, the methods and files, hair physics" with a box (ships unticked, remembered as `spawn_log`) and a box for the words to watch (`spawn_focus`, start: `mia;pl2000;pl2100;em2000;em2200;em2300`).

**What it records**
1. **The methods the game calls.** Three seconds after it is ticked, the script looks through the manager classes this game has (`app.EnemyManager`, `app.CharacterManager`, `app.PlayerManager`, `app.EnemySpawner`, `app.EventManager`, `app.GameManager`, `via.Prefab`, `via.ResourceManager`, and `via.Scene` / `via.GameObject` for create / instantiate names only) and hooks the methods whose names say spawn, create, instantiate, generate, appear, summon, regist, request, load, setup or start, at most 140, five a frame. The first two readable arguments of every call (a name, a file path, a prefab's path) go into a ring of the last 600 calls. A method that fires more than 150 times a second is counted, not logged ("too busy to log").
2. **When she spawns.** Once a second the script looks at every object with a Motion component. A character matching the words that was not there a second ago (or was already there when the log started: said so) starts an **episode**: when, chapter, position, what the game called in the 20 s before (grouped by method: how often, first and last second relative to her spawn, the argument), every call or file that **mentions her** in the last 3 minutes, every file the game was asked for in the 90 s before, and the same for the 25 s after. The scene is left alone while the game is loading.
3. **What she is made of.** Her inventory, five objects a frame: every object under her, its components, and the files they hold: mesh and material, the `.motlist` list of her Motion, and every resource / path getter of her components. Physics components (anything with chain, cloth, hair, spring in the type name) are listed on their own with every number and flag they answer, and with the **method list of their type** in the debug file (`physics_types[...].methods`), which is what the next build needs to set a chain up from real names.
4. **What my copy lacks.** The same inventory of my copy of her (the lab body made from her, or her enemy model), and the difference: objects, component kinds (physics first), files and physics components that the real one has and the copy has not. With no copy standing the log says so; the panel's "Compare the last spawn with my copy" reads it again once one stands.
5. **A census of hair physics.** Every 5 s: which character or enemy carries which physics component (`via.motion.Chain`, `via.motion.ChainCollision`, `via.motion.ChainGroup`, `via.dynamics.GpuCloth`, `via.dynamics.Cloth`, `via.motion.SpringBone`, `app.ChainClothSelector`), on which object, kept between sessions; types this game does not have are said so; characters seen with no physics at all are listed.

**Where it goes:** `re7mp/spawnlog.json` (everything, including her full object list), `re7mp/spawn_log.txt` (the same lines as text; needs `fs.write`, else the lines are in the JSON), and the debug file as `health.spawn_log`. **Send me `spawnlog.json` after you have seen her spawn.**

**Safety:** every read of a component and every hook is announced in `lastcall.json` first (stage `spawnlog`). A session that ended inside one never makes that call again (`re7mp/spawnstate.json`; the panel has a button to forget them). Nothing is hooked while the box is unticked.

**How to use it:** tick the box, play to a place where Mia appears (the flashback, the cutscenes, the fight), let 25 s pass, then send `re7mp/spawnlog.json` and the debug file. To compare with the copy, make the body from her first (Body lab: model `Pl2000` or `Em2000`) and press "Compare the last spawn with my copy".

**Tests:** Lua Scenario 25 (hooks found by name and not the getters, a static method's argument, a prefab's path, the busy-method count, her spawn with the chapter, the calls before it with the name she was spawned with, the files asked for before, her objects / mesh / material / motion lists / chain file / numbers read, the copy difference with objects, files, physics and component kinds, the text log, her leaving, the loading gate, the box off, ticking it in the panel with other words, a hook that ended a session, a component read that ended a session, the census with the missing types).

**Still open:** everything the real game will say about which classes exist; the door gate's skip count and the enemy bank 0 / clip 0 reads from 9.41/9.42; everything that needs a second player.

## What changed in v9.42 (release 0.9; same protocol v6; **update `re7mp.lua` on both computers AND rebuild the exe: the save folder is chosen by Steam account, and the two exes tell each other which account they use**)

Your idea from the 9.41 test: use both players' Steam save-profile ids, the way the other developer's mod knows its players, **without anything going through Steam**. **Unverified in the real game:** the folder choice and the account message are checked with fake Steam folders and two exes on one PC; nothing about a re-signed save loading in the real game has changed (it is still untried).

**What was true before**
- The exe wrote saves into `userdata/<id>/418370/remote/win64_save`, re-signed for the receiver (the account block is copied from any file the receiver's own game wrote, no key needed; unchanged), but it *chose* the folder by "newest file wins", and `re7mp.ini` kept that choice for ever. On a PC with two Steam accounts (yours: 759758082 in use, 1055164497 old) the wrong one is easy to end up on.

**What changed**
1. **The folder is the signed-in account's.** RE7 loads saves from the account Steam is signed in as, so that is the folder to watch. The window reads the account from the registry value Steam keeps up to date (`HKCU\Software\Valve\Steam\ActiveProcess\ActiveUser`; a plain read, nothing is sent to Steam and nothing of Steam's is changed). Steam not running: the account marked `MostRecent` in `<steam>\config\loginusers.vdf` (a plain file read). Neither known: the old rule, and the log says it was a guess. Signed in but that account has **no RE7 folder yet**: no folder at all, and the log says to start RE7 once and reach the main menu (watching another account's folder would be worse).
2. **A stale folder is replaced.** On start-up and again when you press Start, a folder in the box that is a `userdata/<id>/...` path of *another* account than the signed-in one is replaced, and the log line says which account it was and which it is now. A path that is not a userdata folder (typed on purpose) is never touched; neither is the right one.
3. **The two exes tell each other their account (new exe-to-exe message kind 65001, `acct|1|<Steam32 id>`).** Sent once the other player is reachable, again after a break and every minute. The receiving exe consumes it (it never reaches the script; an older exe hands it to its script, which has no handler and ignores it, so there is no wire change and no protocol bump). The id is the folder's name, so a folder that is not a `userdata\<id>` path says nothing. It is a Steam account number, which is not secret, but it is sent: mention it if that matters to anyone you play with.
4. **Both accounts are named everywhere:** the exe's log ("Told the other player's re7mp.exe that this PC uses Steam account X", "The other player's PC uses Steam account Y"), the manifest (`account`, `partner_account`, and `partner_account` on each co-op save: the sender's for a received copy, the receiver's for one you sent), the panel (*Co-op saves*: "Steam accounts: your saves are in account X's folder; the other player's account is Y."), the load-screen scan and the debug file (`coop_saves.account`, `.partner_account`, `.accounts`, and per entry). The same account on both sides is called out (the loopback bot answers with this PC's account, so you can see it solo).

**What it does not do**
- It cannot make a save load for an account that has *never* run RE7: the account block is encrypted with the game's key and the tool has no key (AutostrongSharp's source, MIT, does not contain RE7's; it loads it from a profile file). The receiver still needs one file the game wrote on their account, which any player who got to the main menu once has (`data00-1.bin`).
- The slot number inside the encrypted body is unchanged and a re-signed save has still never been loaded in the real game.

**Tests:** C++ `test_save_accounts` (the message text and its refusals, the account out of a path, `loginusers.vdf`, the folder choice with two accounts including the one that was wrong before, the replacement rules, the manifest fields and a 9.41 manifest without them, two exes swapping accounts with nothing reaching either script, a folder without an account, the loopback bot) and Lua Scenario 24 (the panel line in all four states, the debug file, nonsense values). Full runs: Lua 4492 checks in all (673 new, most of them one "no UI error" check per panel line), none failing; the C++ suite passes in full.

**Still open:** the door gate's high skip count in your 9.41 debug file (3,937 of 5,777 polls), why six of seven enemy types read bank 0 / clip 0, and everything that needs a second player in the real game.

## What changed in v9.41 (release 0.9; same protocol v6; **update `re7mp.lua` on both computers; no exe change**)

The second piece brought over from the other developer's co-op mod ("Molded Together", MIT, see `THIRD_PARTY_NOTICES.md`), rewritten into this script's own messages, notes and tests: **enemy animation, with the bank fetch.** **Unverified in the real game:** everything below ran against the fake game only, and the new box ships **off**.

**What was already true**
- The host has sent every enemy's animation (bank, clip number, frame) along with its position since 9.x, and the joiner never used it. Your 9.38 debug file says the F3 animation probe was never used (`enemy_motions`: "Not used yet", 0 runs), so this build had no animation ids of its own for enemies. The only ones known come from their notes (see `re7-findings.md`).

**What changed**
1. **A table of every bank and clip the game shows on an enemy (always on, costs next to nothing).** The host records each (bank, clip) it reads on each enemy, with how often and the largest frame seen, and finds the `.motlist` path of each bank (the Motion's dynamic banks first, then its active banks, then the probe's index route; three tries a bank, never faster than twice a second). It is in the debug file as `health.enemy_clips` and kept between sessions in `re7mp/enemy_clips.json`. **This is how the enemies' animation ids get known from the game itself:** play, then send that file.
2. **The joiner can play the host's clip on its own enemy (new box, off, remembered as `enemy_clips`).** Panel > Enemies > *Enemy sync* mode 3 > *Also switch off their AI* > **EXPERIMENTAL: play the host's enemy animations on my enemies**. Their calls: the enemy's own `MotionFsm` is switched off (and put back to what it was), and layer 0's six-parameter `changeMotion(bank, clip, frame, 8.0, 2, 0)` plays the clip (floats for the numbers). The frame is put right only when it has drifted by more than 8 frames, at most once a second.
3. **The bank fetch (new message kind 14).** A clip whose bank my copy has not loaded would leave it in a T-pose (their Mia, in every grab and when Ethan blocked her chainsaw). `getMotionInfo(bank, clip, info)` says whether the copy has it; when it does not, the copy keeps its last move and asks the host: `req|<enemy>|<bank>|<ch>` (at most 4 times a bank, 2 s apart). The host answers `bank|<enemy>|<bank>|<overwrite>|<path>|<ch>` (or `none|...|<why>|<ch>`) whether or not its own box is ticked, and the copy adds the bank (a `DynamicMotionBank` with the path's resource, `set_OverwriteBankID`, `set_BankID`, appended, then `setupMotionBank`, without which an added bank stayed inactive) and plays the clip. Paths are checked before use (`.motlist`, letters, digits, `_ . / -`, no `..`, 130 characters at most); at most 12 banks are added a session; a bank that fails is not tried again.
4. **It lets go:** box off, mode or AI box changed, the host quiet for 3 s, its enemy dead or parked, the game loading (the 9.40 gate), or an enemy being saved (their finding: a saved enemy keeps its think state, so `app.EnemySave.prepareToSave` puts the animation controller back and pauses the clips for 4 s). Three errors on one enemy switch its clips off for the session. A call that cannot tell whether the copy has a clip lets it play, counted as "unsure" (their rule).
5. **The panel** shows the box, why it is idle (`off`, `needs Enemy sync mode 3`, `needs the box 'Also switch off their AI'`, `this game is the host`, `no enemy data from the host`, `the game is loading`, `the game is saving`, or `playing`), the counts and the last message.

**Debug file:** `health.enemy_clips` (state, counters, what is playing, the table of clips with `copy_has_it`, the table of bank paths, the last 30 messages with their results, the last error).

**Tests:** 276 new Lua checks, 3819 in all, none failing (a fake Em2000 whose Motion answers `getMotionInfo`, the dynamic and active banks, `setupMotionBank` and the six-parameter `changeMotion`; its `MotionFsm` is a component of its own): the host's table and file, answers and refusals, nonsense messages, a request while loading or from another chapter, playing and the drift rule, a missing bank asked for 4 times and then added, refused paths, a resource that cannot be made, every way of letting go, three errors, a `getMotionInfo` that fails.

**Still open:** everything about it in the real game (whether `changeMotion` on a scene enemy with the AI box ticked looks right, whether the animation controller stays off, the real paths of the banks); what the model copies of enemies (the "Enemy models" boxes, which have no Motion component) need to animate: their copy of Mia got a motion bank asset, a joint map and a hand-made layer (`set_Resource(nil)` first) before it walked, which is the next piece; the grab and execution moves.

## What changed in v9.40 (release 0.9; same protocol v6; **update `re7mp.lua` on both computers; no exe change**)

The first feature brought over from the other developer's co-op mod ("Molded Together", MIT, see `THIRD_PARTY_NOTICES.md`), one piece per build, rewritten into this script's own messages, notes and tests: **doors**. **Unverified in the real game:** everything below ran against the mock game only. Their notes say their door sync was tested live (two two-player sessions, up to the Chapter 3 yard); this script's version of it has not been.

**What changed**
1. **Doors are shared (new message kind 13).** When one player unlocks, opens, closes or pushes a door, the same happens to that door in the other game. Opening uses the six-argument `requestAutoOpen` with the door's own speed (their notes: the one-argument call did nothing on 87 of 106 remote opens of the latched main-house doors), closing uses `requestAutoClose`, a push is sent as its angle (at most 5 a second, only when it moved 3 degrees) and the other game glides the door to it with `requestPush`. A door that stays locked after the unlock is unlocked again (up to 3 times, a second apart). A door that did not start opening after 0.7 s is snapped open.
2. **A door that swings shut by itself is not sent as a close** (their notes: sending it slammed the door on the other player as they walked through). A close is sent when my player used the door (a hook on `DoorPush.setInteract`), or when it is a door I opened. The self-close belongs to the game of whoever opened the door: the other copy waits for its close; a door I opened does not shut while the other player stands in the doorway; their close waits while I stand in the doorway, and happens when I step out.
3. **The loading gate (`CFG.busy`).** While the game loads a scene, jumps chapter or swaps the player, nothing is called on a door (their 2026-11-10 session: about 250 exceptions a second inside the game, then a hang or a crash). The gate is shut during a load and for a second after, gives up after 3 minutes, and the doors are read again from scratch afterwards (what changed meanwhile is not sent as news). An unlock that arrives during a load, or for a door that is not loaded yet, is kept and applied when the door is there. Other messages for a door that is not there are dropped and counted.
4. **Doors cost nothing in solo play:** with nobody connected no door is scanned. Connected, the scene is scanned 4 times a second for `app.DoorPush`; the debug file says what that costs (`health.doors.poll_avg_ms`, `poll_worst_ms`).
5. **A message from another chapter is ignored** (each door message carries the chapter number).
6. **The panel has a *Doors (shared with the other player)* section:** a box to switch it off (remembered as `door_sync`, on by default), the counts, the last message and the last six sent or received with what became of each. **The debug file has `health.doors`:** every counter (sent, got, applied, not loaded here, other chapter, dropped while loading, retries, snaps, errors), the last 40 messages with their result, the doors known with their state, and `loading_gate` (how often it shut, for how long, why).

**Messages (kind 13, the pieces joined with `|`; the last piece is the chapter):** `open|<id>|<ch>`, `close|<id>|<ch>`, `unlock|<id>|<ch>`, `angle|<id>|<degrees>|<side>|<ch>`. The id is the door's `SaveGUID`, the same in both games.

**Tests:** 288 new Lua checks, 3543 in all, none failing (a fake `app.DoorPush` with the states, the six-argument open, a latched door, a door that needs two unlocks, an array without `get_elements`, a scan that fails, the loading flags, the chapter, the switch, solo play, nonsense messages). The exe and the C++ tests are unchanged. The first full run found that the door scan ran in solo play (three older "no scan with nobody connected" checks failed); fixed before the build.

**Still open:** everything about it in the real game (the door hook's argument slots, the cost of the scan, the glide of a pushed door over this script's message channel instead of their 30 Hz relay); the van door at the start is not a `DoorPush` and is not covered; drawers, switches and one-off interactions (the van, fridge, pot) are the next pieces, then the animated bodies for scripted interactions.

## What changed after v9.24 (exe part of v9.25): co-op saves are re-signed for the receiver (release 0.9; same protocol v6; **exe only: rebuild `re7mp.exe` on both computers**; shipped together with v9.25)

It answers your note "saves dont sync properly" (RE7 saves are tied to the Steam account that wrote them) and the files you attached: AutostrongSharp's source, and `data003Slot.bin` twice (the two files are byte-identical, so there was no re-signed twin to compare; it was not needed).

**What I found.** In an RE7 save only two things depend on the Steam account: one 8-byte block of the 48-byte header, and the Murmur3 checksum in the last 4 bytes (everything else, the encrypted save, does not). The checksum code from AutostrongSharp, ported to C++, reproduces the checksum in your real save, in the sample save from the AutostrongSharp repository and in the original tool's two test files. So the receiver can re-sign a save **without the game's key**: take the account block from the saves the game itself wrote on the receiver's account, put it in the incoming file, recompute the checksum.

**Changed.**
1. *`src/save_resign.hpp/.cpp` (new).* The checksum, a reader for the header, `find_own_mark` (learns your account from your folder's saves: first 48 bytes of each `.bin`, copies this tool installed are ignored, the majority wins, a tie is refused), `resign_save` and `resign_for_this_pc`.
2. *`src/engine.cpp`.* A received save goes through `resign_for_this_pc` before it is written. It is installed re-signed, unchanged (not an RE7 save container, so the old behaviour), or **refused with a plain-English reason** (no save of your own in the folder yet, your folder's saves disagree, the file is damaged or encrypted with another key). The manifest and the read-back check use the checksum of what is on disk. No packet changed.
3. *Tests.* `tests/data/autostrong_test_*.bin` (the original tool's two test files, MIT, with a note), unit tests for the checksum, the header, the re-signing round trip (re-signing back gives the original bytes), every refusal, the folder scan; a TCP test where Alice's save arrives naming Bob's account with the body byte for byte hers, files that are not saves still arrive unchanged, and a Bob with no save of his own is refused. 22 deliberate breakages of the new code were caught by the quick unit run (`RE7MP_ONLY_RESIGN=1 ./re7mp_tests`), and two of the engine change by the full run.

- **Health:** read from the `HealthInfo` object inside the enemy's DamageController (the Status components have no HP field). Dead enemies disappear.
- **Items:** the panel now lists your inventory with **Give 1 / Give all** buttons per item, so giving no longer depends on the cursor hook that never fired in your test. Button 7 works even when nothing is pointed at and dumps the inventory list.
- **Damage trace (button 6):** finds each live enemy's own damage and health types and prints damage records with their numbers.
- **Other player's hide distance:** default 0.4 m (was 0.8 m), with a slider in the panel; remembered.
